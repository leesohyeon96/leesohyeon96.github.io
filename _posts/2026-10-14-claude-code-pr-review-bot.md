> ✍️ 이 글은 AI 의 도움을 받아 정리했지만, 만든 것과 겪은 일, 생각은 전부 내 머리에서 나왔다.

> Claude Code 로 "내게 온 리뷰 요청"을 자동으로 처리하는 봇을 만들었다.
> 근무 시간엔 내 PC 에서 3분마다, 퇴근 후와 주말엔 GitHub 서버에서 30분마다 돈다.

## 왜 만들었나

우리 팀은 PR 하나를 머지하려면 승인 1명이 필요하다. 팀원 넷이 서로를 리뷰어로 거는 구조라, 하루에도 몇 번씩 리뷰 요청 알림이 온다.

문제는 리뷰가 늦어지는 이유가 대부분 **"바빠서 못 열어 봤다"** 라는 점이었다. 막상 열어 보면 큰 문제가 없는 PR 이 대부분인데, 내가 다른 일에 빠져 있거나 퇴근한 사이에 동료의 작업이 멈춰 있었다.

반대로 꼼꼼히 보려다가 과하게 파고드는 일도 있었다. 의존성 파일 세 개짜리 PR 에서 패키지 하나의 영향을 끝까지 추적하느라 도구 호출을 18번 쓴 적이 있다. 그 정도 PR 에 그만한 비용이 매번 드는 건 원하는 그림이 아니었다.

그래서 목표를 이렇게 잡았다.

1. 리뷰 요청이 오면 **사람이 없어도** 빠르게 1차 리뷰가 달린다.
2. 기본은 **신뢰하고 승인**, 정말 위험한 것만 멈추고 나를 부른다.
3. **무엇을 봤고 무엇을 안 봤는지**를 리뷰에 항상 적는다.

## 전체 구조

```
동료가 PR 에 나를 리뷰어로 지정
            │
            ▼
GitHub "나에게 온 리뷰 요청" 목록
            │  먼저 가져간 쪽이 한 번만 처리
   ┌────────┴─────────┐
   ▼                  ▼
평일 08:00~17:00      그 밖의 시간 · 주말 · 노트북 절전
내 PC 작업 스케줄러     개인 private 레포 GitHub Actions
3분마다                30분마다 (GitHub 서버)
   └────────┬─────────┘
            ▼
요청이 있을 때만 Claude 를 깨움
            ▼
CLAUDE.md 규칙대로 리뷰
   ├ 문제 없음   → 승인 + 코멘트
   └ 심각한 문제 → 승인 없이 코멘트 + 나를 @멘션
            ▼
리뷰가 달리면 요청 목록에서 자동으로 빠짐 → 중복 리뷰 없음
```

같은 규칙 파일(`CLAUDE.md`)과 같은 지시문을 **두 곳이 공유**한다. 어디서 돌든 동작은 똑같다.

## 리뷰 규칙 — 봇의 성격을 정하는 파일

봇이 어떻게 행동할지는 전부 `CLAUDE.md` 한 파일에 적혀 있다. 이 규칙의 뼈대는 팀 동료가 먼저 쓰던 것을 받아서 내 상황에 맞게 고친 것이다.

### 기본 스탠스: PR 작성자를 신뢰한다

- 리뷰는 **승인이 기본값**이다.
- 기본은 **빠르게 훑기**. diff 를 읽고 바로 코멘트한다.
- 훑다가 걸린 것만 깊이 판다.
- 작성자가 코멘트를 읽고 알아서 처리할 거라고 믿는다. 그래서 사소한 지적은 **승인과 함께** 남긴다.

### 멈추는 기준은 딱 세 가지

| 승인을 보류하고 나를 부른다 | 한 줄만 남기고 넘어간다 |
|---|---|
| 보안 | 특정 조건이 갖춰져야 터지는 잠복형 위험 |
| 데이터 손실 | 스타일 · 일관성 |
| 런타임 파손 | 문서 미비 |

"잠복형 위험"을 따로 둔 게 핵심이다. 성격은 보안이나 런타임 문제지만 지금 당장은 발현되지 않는 것들이다. 이걸 끝까지 추적하면 앞에서 말한 18번짜리 리뷰가 된다. 그래서 **사실만 한 줄 적고 넘어가라**고 명시했다.

### 리뷰 본문의 틀

```
(무엇을 위주로 봤는지 한 줄) 승인합니다.

**확인한 것**
- diff 근거 항목

**한 줄 메모**          ← 있을 때만
- 잠복형 · 문서 미비 등

**확인하지 않은 것**
- 이번에 보지 않은 범위
```

**"확인하지 않은 것"** 칸을 꼭 두었다. AI 리뷰가 "승인합니다" 한 줄만 남기면 사람은 그게 얼마나 믿을 만한지 알 수 없다. 어디까지 봤는지를 적어 두면, 리뷰를 받은 사람이 나머지를 스스로 판단할 수 있다.

### 팀의 맥락도 규칙에 넣는다

리뷰봇이 매번 같은 걸 "심각하다"고 올리면 금방 아무도 안 읽는 봇이 된다. 그래서 **이미 팀에서 판단이 끝난 사안**은 규칙에 적어 두고 다시 문제 삼지 않게 했다. 반대로 우리 레포에서 자주 빠뜨리는 것(설정값을 추가했는데 배포 문서를 안 고쳤다든지)은 "한 줄로 짚을 것" 목록으로 넣었다.

## 1. 컴퓨터가 켜져 있을 때 — 내 PC (3분)

근무 시간에는 내 PC 가 맡는다. 처음엔 Claude Desktop 의 예약 작업(Routine)으로 3분마다 Claude 를 깨웠는데, 지금은 **윈도우 작업 스케줄러 + 작은 스크립트**로 바꿨다. 이유는 아래 "토큰을 94% 줄인 이야기"에 있다.

```
[윈도우 작업 스케줄러] 평일 08:00~17:00, 3분마다
        ▼
run-review.ps1
   ├ gh 로 리뷰 요청 개수만 확인 (토큰 0, 1초)
   ├ 0건  → 그냥 끝
   └ 1건+ → 그때만 claude -p 로 Claude(Opus) 실행 → 리뷰
```

Claude 에게 주는 지시문은 짧다.

```
이 폴더의 CLAUDE.md 에 적힌 "자동 리뷰 — 매 실행 동작" 을 한 번 수행해.
- 리뷰 요청된 열린 PR 이 없으면 "리뷰 요청 없음" 한 줄만 출력하고 끝낸다.
- 있으면 CLAUDE.md 규칙대로 리뷰한다.
- 반드시 Bash 도구로, gh 명령만, 한 번에 하나씩.
- 머지 · 닫기 · 푸시는 절대 하지 않는다.
```

봇이 하는 일은 사실상 `gh` 명령 네 개뿐이다.

```bash
gh search prs --review-requested=@me --state=open   # 내게 온 리뷰 요청
gh pr view <번호> --repo <owner/repo>                # 제목 · 본문
gh pr diff <번호> --repo <owner/repo>                # 변경 내용
gh pr review <번호> --repo <owner/repo> --approve --body '...'
```

로컬에서 돌리는 가장 큰 장점은 **리뷰가 내 계정 이름으로 달린다**는 것이다. 동료 입장에선 "봇이 뭐라 했다"가 아니라 내가 리뷰한 것으로 보이고, 머지 조건(승인 1명)도 그대로 채워진다.

### 삽질: 무인 실행인데 자꾸 허락을 묻는다

첫 실전에서 리뷰와 승인까지는 성공했다. 그런데 중간에 **허락 창이 두 번** 떴다. 무인 실행에서 허락 창이 뜨면 그 자리에서 멈춘다.

원인을 보니 Claude 가 명령을 이렇게 섞어 쓰고 있었다.

```bash
cd 어딘가; gh pr diff 123 | wc -l
gh pr diff 123 > /tmp/diff.txt
mkdir tmp; cat > tmp/body.md
```

미리 허용해 둔 건 `gh pr diff` 같은 단일 명령인데, `cd` 와 파이프, 리다이렉트가 붙으면 다른 명령으로 판단돼 다시 묻는 것이다. 그래서 규칙에 **"명령 사용 규칙"** 을 추가했다.

- 허용된 `gh` 명령 네 개만 쓴다.
- `;` `&&` `|` 로 잇지 않는다. `cd` 를 앞에 붙이지 않고 항상 `--repo` 를 쓴다.
- 파일을 만들지 않는다. 리뷰 본문은 `--body` 로 직접 넘긴다.

며칠 뒤 또 한 번 허락 창이 떴다. 이번엔 **PowerShell 로 실행된 날만** 그랬다. 리뷰 본문에는 마크다운 코드 표기용 백틱(`` ` ``)이 잔뜩 들어가는데, PowerShell 에서 백틱은 이스케이프 문자다. 그래서 본문이 깨지고, 허용 규칙이 있어도 안전한지 판단을 못 해 다시 물었다. 같은 날 Bash 로 돈 실행은 문제가 없었다.

그래서 규칙에 한 줄을 더 넣었다. **"반드시 Bash 로, 리뷰 본문은 작은따옴표로 감싼다."**

여기서 배운 것: **규칙은 유도일 뿐 강제가 아니다.** AI 가 어떤 도구를 고를지는 매번 조금씩 다르다. 그래서 문제가 생기면 실행 기록에서 실제로 어떤 명령을 썼는지 뽑아 보고 규칙을 보강하는 식으로 다듬어 가고 있다.

## 토큰을 94% 줄인 이야기

일주일쯤 돌린 뒤 실행 기록 671건의 토큰 사용량을 뽑아 봤다. 결과가 생각보다 컸다.

### 과거: 할 일이 없어도 3분마다 Claude 를 깨웠다

- 실행의 **94%가 "리뷰 요청 0건"** 이었다. 그런데도 매번 Claude 가 깨어나서 시작 자료(규칙 · 도구 설명 · 설치된 스킬 목록 등) 약 6만 4천 토큰을 읽었다.
- 게다가 지시문의 **"요청이 없으면 아무 말 없이 끝낸다"** 가 역효과였다. 출력이 비면 Claude Code 가 "답이 없다"며 다시 물어서, 빈 실행마다 API 호출이 한 번씩 더 생겼다.
- 그래서 하루(3분 주기, 172회 실행)에 **입력 3,730만 토큰**이 찍혔다. 대부분은 캐시 읽기라 값은 할인되지만, 그래도 실제 비용 기준 약 770만 토큰어치였다.

### 바꾼 것

1. **Claude 를 깨우기 전에 스크립트가 먼저 본다.** `gh` 로 요청 개수만 확인하고, 0건이면 Claude 를 아예 실행하지 않는다. (퇴근 후 GitHub Actions 는 처음부터 이렇게 하고 있었다.)
2. **"아무 말 없이 끝낸다" → "`리뷰 요청 없음` 한 줄 출력"** 으로 바꿔 헛호출을 없앴다.
3. 모델은 **Opus 그대로**. 리뷰 품질은 포기하지 않았다.

### 얼마나 줄었나 (하루 기준)

| | 과거 | 지금 |
|---|---|---|
| 확인 주기 | 3분 | 3분 (그대로) |
| Claude 를 깨우는 횟수 | 약 170회 | 리뷰 있을 때만 (약 6회) |
| 빈 실행 1회 비용 | 약 19만 토큰 | **0** |
| 하루 입력 토큰 | 약 3,730만 | 약 240만 |
| 실제 비용 기준 | 약 770만 | 약 50만 (**약 94% 감소**) |

> 지금 수치는 일주일 동안의 리뷰 실행 평균(하루 약 6건 × 약 40만 토큰)으로 추정한 값이다.

덤으로 Claude Desktop 앱을 계속 켜 둘 필요가 없어져서, 앱이 쓰던 메모리(약 730MB)도 아끼게 됐다.

교훈: **AI 에게 "할 일이 있는지 확인하는 일"까지 시키지 말자.** 그건 스크립트 한 줄이면 된다. AI 는 판단이 필요한 순간에만 부른다.

## 2. 컴퓨터가 꺼져 있을 때 — 개인 레포 GitHub Actions (30분)

PC 쪽은 PC 가 켜져 있어야 돈다. 퇴근하거나 노트북이 절전에 들어가면 멈춘다. 그 시간은 **GitHub 서버**가 맡게 했다.

### 왜 회사 레포가 아니라 개인 레포인가

회사 레포에 Actions 를 붙이면 리뷰가 봇 계정 이름으로 달린다. 나는 **내 이름으로** 승인이 달려야 했다. 그래서 개인 **private** 레포를 하나 만들고, 거기서 내 GitHub 토큰으로 `gh` 를 돌리게 했다. 규칙 파일에 팀 내부 사정이 적혀 있으니 레포는 반드시 private 이어야 한다.

### 워크플로

{% raw %}
```yaml
on:
  schedule:
    - cron: '7,37 8-23 * * 1-5'    # 평일 KST 17:00 ~ 다음날 08:59
    - cron: '7,37 * * * 0,6'       # 주말 종일
  workflow_dispatch: {}            # 수동 실행 버튼

concurrency:
  group: pr-review-bot
  cancel-in-progress: false        # 앞 실행이 리뷰 중이면 기다린다

jobs:
  review:
    runs-on: ubuntu-latest
    env:
      GH_TOKEN: ${{ secrets.GH_TOKEN }}       # 내 토큰 → 내 이름으로 동작
    steps:
      - name: 리뷰 요청 확인 (Claude 를 띄우기 전에)
        id: queue
        run: |
          n=$(gh search prs --review-requested=@me --state=open --draft=false --json number -q 'length')
          echo "count=${n}" >> "$GITHUB_OUTPUT"

      - uses: actions/checkout@v4
        if: steps.queue.outputs.count != '0'

      - run: npm install -g @anthropic-ai/claude-code
        if: steps.queue.outputs.count != '0'

      - name: 리뷰 실행
        if: steps.queue.outputs.count != '0'
        env:
          CLAUDE_CODE_OAUTH_TOKEN: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
        run: |
          claude -p "$(cat desktop-instruction.txt)" \
            --allowedTools "Bash(gh search prs:*)" "Bash(gh pr view:*)" "Bash(gh pr diff:*)" "Bash(gh pr review:*)" "Read" \
            --disallowedTools "Bash(gh pr merge:*)" "Bash(gh pr close:*)" "Bash(git push:*)" \
            --max-turns 40
```
{% endraw %}

몇 가지 신경 쓴 부분이 있다.

- **cron 은 UTC 다.** KST 에서 9시간을 빼야 한다. 평일 KST 17:00 은 UTC 08:00 이다.
- **정각을 피했다.** GitHub 의 예약 실행은 정각에 몰려서 늦어지기 쉽다. 그래서 7분과 37분에 돌린다.
- **Claude 를 띄우기 전에 큐부터 본다.** 리뷰 요청이 0건이면 Claude 설치도 실행도 하지 않는다. 대부분의 실행은 여기서 몇 초 만에 끝난다.
- **위험한 명령은 명시적으로 막았다.** 머지 · 닫기 · 푸시는 `--disallowedTools` 로 차단했다.

### 비용 계산

private 레포의 Actions 는 무료 한도가 월 2,000분이다. 실행 1회는 최소 1분으로 과금된다.

```
30분 주기 × (평일 밤 16시간 + 주말 48시간) ≈ 월 1,100회
1,100회 × 1분 ≈ 1,100분  →  무료 2,000분 안
```

Claude 사용량은 리뷰 요청이 있을 때만 든다. 빈 큐에서는 Claude 를 아예 부르지 않기 때문이다.

### 다른 방법은 왜 안 썼나

| 방법 | 안 쓴 이유 |
|---|---|
| 회사 레포 Actions | 리뷰가 봇 이름으로 달린다 |
| Claude Code `/loop` | 창을 닫으면 멈추고, 7일 뒤 만료된다 |
| Cloud Routine | 예약 주기가 최소 1시간이고, 조직에 앱 설치가 필요하다 |
| 로컬만 사용 | 노트북이 절전이면 멈춘다 |

## 중복 리뷰는 어떻게 막나 — 상태 파일이 필요 없다

두 곳이 동시에 돌면 같은 PR 에 리뷰가 두 번 달리지 않을까? 처음엔 "처리한 PR 목록"을 어딘가 저장해야 하나 고민했는데, 필요 없었다.

**리뷰를 제출하면 GitHub 이 그 PR 을 "나에게 온 리뷰 요청" 목록에서 자동으로 뺀다.** 그래서 큐를 조회하는 쿼리(`--review-requested=@me`) 자체가 중복 방지 장치다. 업무 시작 직후 한 시간은 두 곳이 겹쳐 도는데, 먼저 리뷰한 쪽이 처리하면 다른 쪽 조회에는 그 PR 이 더 이상 안 보인다.

PC 쪽은 한 가지를 더 막았다. 리뷰 하나가 3분보다 오래 걸리면 다음 실행이 같은 PR 을 또 집을 수 있어서, 스크립트가 **이전 실행이 끝나지 않았으면 그냥 건너뛰게** 했다.

작성자가 수정한 뒤 다시 리뷰를 요청하면 목록에 다시 나타나고, 봇이 다시 리뷰한다. 이건 의도한 동작이다.

## 이것도 AX 라고 할 수 있을까?

AX(AI Transformation)는 보통 조직이 일하는 방식 자체를 AI 중심으로 바꾸는 걸 말한다. 그 기준으로 보면 이건 조직 단위의 변화는 아니고, **내 업무 흐름 하나를 바꾼 개인 단위의 작은 AX** 정도가 정직한 표현 같다.

그래도 AX 의 핵심 요소는 다 들어 있다고 생각한다.

- **사람이 하던 판단을 AI 에게 넘겼다.** 단순히 알림을 보내는 자동화가 아니라, diff 를 읽고 승인 여부를 판단하는 일을 맡겼다.
- **판단 기준을 글로 명시했다.** "언제 승인하고 언제 멈추나"를 규칙 파일로 만들었고, 그 과정에서 내가 리뷰할 때 무엇을 중요하게 보는지가 오히려 분명해졌다.
- **사람은 예외만 본다.** 평소엔 봇이 처리하고, 보안 · 데이터 손실 · 런타임 파손일 때만 내가 불려 온다.
- **운영하면서 고친다.** 허락 창 문제와 토큰 사용량처럼, 실제로 돌려 보고 실행 기록을 보며 다듬는다.

## 주의할 점

편한 만큼 조심해야 할 것도 분명하다.

- **봇의 승인이 곧 머지 허용이다.** 승인 1명이 머지 조건이라, 봇이 승인하면 바로 머지할 수 있다. 그래서 "확인하지 않은 것"을 꼭 적게 했고, 멈추는 기준(보안 · 데이터 손실 · 런타임 파손)은 보수적으로 두었다.
- **토큰이 새면 내 이름으로 승인이 된다.** GitHub 토큰은 최소 권한과 만료 기한을 두는 게 맞다. (지금은 넓은 권한 토큰을 쓰고 있어서 최소 권한 토큰으로 바꿀 예정이다.)
- **AI 리뷰는 사람 리뷰를 대신하지 않는다.** 1차로 빠르게 훑어 주는 역할이다. 큰 설계 변경은 여전히 사람이 직접 본다.

## 마치며

만들고 나서 가장 크게 달라진 건 **동료의 PR 이 내 일정 때문에 멈추지 않는다**는 점이다. 그리고 의외의 수확은 규칙 파일이었다. "나는 리뷰할 때 뭘 보지?"를 글로 적어 보니, 내가 어디서 시간을 과하게 쓰는지가 보였다.
